# find-context

Сбор **проверенного current-state контекста** под бриф. Выход — `CONTEXT_DOC`
(`Feature-context/<slug>.md`), основной источник фактов для `/write-feature`.

Пути и токены: правило `artifact-paths`.

## Pipeline

```
/find-context → /write-feature → /check-feature → …
```

| | Путь |
|---|------|
| **Вход** | бриф (текст после команды) |
| **Области поиска** | `analytics/`, `Feature-writing/`, `repositories/`, `db-export/`, `auxiliary/` |
| **Выход** | `CONTEXT_DOC` |
| **Рабочий файл** | `Feature-context/<slug>-discovery.md` |
| **Не трогаем** | `repositories/`, `SPEC` других фич |

Приоритет источников: [reference.md](reference.md).

---

## Шаг 0. Вход

1. Весь текст после `/find-context` — **бриф**. Нет текста → попроси бриф и стоп.
2. Выведи `<slug>` из брифа: `kebab-case-descriptive`, латиница
   (например `og-trading-order-yield`). Не использовать `update`, `changes`, `wip`.
3. Если `CONTEXT_DOC` уже существует — спроси: дополнить или перезаписать.

---

## Шаг 1. Discovery (скрипт)

Из корня workspace:

```bash
python3 scripts/find_context.py "<бриф>" --name <slug> --out Feature-context/<slug>-discovery.md
```

Скрипт выделит термины и вернёт ранжированные таблицы кандидатов по областям.
Опции при слабом результате: `--terms "доп термины"`, `--doc-limit N`, `--code-limit N`.

Если кандидатов мало — перезапусти с уточнёнными `--terms` (доменные имена,
названия сервисов, полей, методов + термины из § «Фокус поиска»), затем
дополни ручным поиском по коду.

---

## Шаг 2. Проверка находок

1. Прочитай discovery-пакет.
2. Сначала открой кандидатов из § «Фокус поиска» пакета (`.proto` / RPC
   или liquibase / `db-export/`), затем остальные сверху вниз по score.
3. **Не подтверждай факт по имени файла** — открой и убедись: класс, метод,
   endpoint, proto-сообщение, таблица, колонка, конфиг-ключ.
4. Для каждого факта фиксируй **путь + якорь** (класс/метод/таблица/строки).
   Для контракта обязательны service / rpc / message / поля; для данных —
   таблица / колонка / changeset. Нет якоря → `Q-XX`.

| Тип факта | Источник истины |
|-----------|-----------------|
| Бизнес-требования, AS IS / TO BE | `analytics/` |
| Контракты, поля, классы, миграции | `repositories/` |
| Схема БД (справочник) | `db-export/` |
| Соседние фичи, согласование контрактов | `Feature-writing/*/` |

При конфликте analytics и кода: для технических фактов **код побеждает**;
расхождение зафиксируй как `Q-XX`.

---

## Шаг 3. Заполнить документ-контекст

Заполни скелет из discovery-пакета. Обязательные блоки:

| Блок | Содержание |
|------|------------|
| Задача (бриф) | Цитата брифа + трактовка |
| Затронутые области | Область → что затрагивается → документы/код |
| Релевантная аналитика | Документ → что описывает → почему релевантно |
| Релевантный код | Файл → компонент → текущее поведение → почему важно |
| Данные | Таблица/поле → где найдено → устройство → влияние |
| Интеграции и контракты | Что учесть, термины домена |
| Ограничения и риски | Текущее состояние, обратная совместимость |
| Что учесть при написании фичи | Практические указания для `/write-feature` |
| Открытые вопросы | `Q-01`, `Q-02`, … + где искать ответ |

Правила:

1. Это **current-state контекст**, а не проектирование — не придумывай решение.
2. Непроверенное → `Q-XX` в «Открытые вопросы», **не** выдумывай поведение.
3. Каждый `Q-XX` — с колонкой «Где искать ответ» (команда, файл, владелец).
4. Язык — русский; имена полей, классов, API — как в исходниках.
5. Не оставляй `INTERNAL`, score-таблицы, служебные строки скрипта.

---

## Шаг 4. Сохранить

1. Запиши `CONTEXT_DOC` = `Feature-context/<slug>.md`.
2. Удали discovery-пакет: `rm -f Feature-context/<slug>-discovery.md`.
3. `FEATURE_DIR` **не создавай** — это делает `/write-feature`.

---

## Шаг 5. Ответ пользователю

Кратко на русском:

- путь к `CONTEXT_DOC`;
- сколько подтверждённых фактов и сколько `Q-XX` осталось;
- 2–3 ключевых риска / находки;
- **Next:** `/write-feature <бриф>` (тот же `<slug>`).

---

## Антипаттерны

- ❌ Подтверждать факт по имени файла без чтения содержимого
- ❌ Проектировать TO BE в контекст-документе
- ❌ Оставлять `INTERNAL` / score-таблицы в финальном документе
- ❌ Выдумывать поведение вместо `Q-XX`
- ❌ Править `SPEC` или код в `repositories/`
