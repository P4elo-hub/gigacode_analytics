# resolve-gaps

Интерактивное закрытие **открытых gaps**: реестр `[GAP-...]` → **кластеры по
Q-XX** (один вопрос на тему) → варианты в `DECISIONS` → оркестратор спрашивает
→ **переписать** затронутые § `SPEC` и **удалить** gaps. Карта закрытых gaps —
в `GAPS_MAP`, не в теле спецификации.

Отличие от `/resolve-code-alignment`: источник — **сама спецификация** и
контекст-док, а не отчёт `ALIGNMENT`.

Пути и токены: правило `artifact-paths`.

## Pipeline

```
/write-feature → /check-feature → /resolve-gaps → /challenge-feature → …
```

| | Путь |
|---|------|
| **Вход** | `SPEC` = `Feature-writing/<slug>/<slug>.md` |
| **Контекст** | `CONTEXT_DOC` = `Feature-context/<slug>.md` (если есть) |
| **Ответы** | `DECISIONS` = `Feature-writing/<slug>/<slug>-decisions.md` |
| **Правим** | `SPEC` (содержательные §) + `CONTEXT_DOC` (§ закрытых Q) |
| **Выход (карта)** | `GAPS_MAP` = `Feature-writing/<slug>/<slug>-gaps-resolved.md` |
| **Не трогаем** | `repositories/`, `ALIGNMENT`, `CHALLENGES` |

Детали извлечения gaps и шаблоны вариантов: [reference.md](reference.md).

---

## Шаг 0. Разрешить slug

1. Аргумент: `<slug>` **или** путь к `SPEC`.
2. Нет `SPEC` → стоп: сначала `/write-feature`.
3. Опциональный **фокус** — список `GAP-...` / `Q-XX` (только их опросить).

---

## Шаг 1. Собрать реестр открытых gaps

Прочитай **целиком** `SPEC`. Дополнительно — `CONTEXT_DOC` для формулировок
`Q-XX` и контекста вариантов.

| Источник | Как искать |
|----------|------------|
| Таблицы `**Gaps и допущения:**` | Строки с `Тип` = `Gap` / `Допущение`; строки `Закрыт` (legacy) — мигрировать в карту и удалить из `SPEC` |
| Inline-маркеры | `[GAP-...]` в тексте, таблицах, use case |
| Связанные `Q-XX` | Q из `CONTEXT_DOC`, на которые ссылается gap |

### Дедупликация и исключения

- Один `GAP-*` id — **один** след в spec, даже если встречается в нескольких §.
- **Единица опроса — кластер**, не отдельный GAP: несколько GAP на один `Q-XX` →
  **одна** строка `DECISIONS`, все id в колонке Relates.
- GAP без явного Q в строке — привяжи по смыслу к `Q-XX` из `CONTEXT_DOC` §
  «Открытые вопросы» или sibling GAP с тем же текстом (см. [reference.md](reference.md)
  § «Кластеризация»).
- Исключать: GAP как TO BE implementation, дубликаты без нового смысла.

Если **открытых gaps = 0** → сообщи и **стоп** (файлы не править).

### 1.1 Кластеризация (обязательно, до вариантов)

1. Собери уникальные `GAP-*` из `SPEC`.
2. Для каждого GAP найди связанный `Q-XX` (inline, таблица, context-doc).
3. Сгруппируй: `Q-01 → [GAP-GOAL-04, GAP-INT-01, …]`.
4. Выведи таблицу кластеров в ответ оркестратору (Q / GAP count / ids).
5. **Не** обрабатывай GAP по одному — только кластеры.

| Открытых GAP | Батч needs-answer |
|--------------|-------------------|
| ≤ 15 | все кластеры одним проходом |
| > 15 | **батч 1:** blockers (контракт, UC, BR); **батч 2+:** после apply батча 1 |

---

## Шаг 2. Подготовить варианты решения

Для **каждого кластера** (Q-XX или группа orphan GAP с одной темой) сформируй
2–4 **конкретных** варианта до опроса:

1. Прочитай § вокруг **любого** GAP кластера и формулировку `Q-XX` в
   `CONTEXT_DOC`.
2. Допустимые источники на этом шаге: `CONTEXT_DOC`, sibling-spec в
   `Feature-writing/*/`, якоря в `analytics/`.
3. ❌ **Запрещено** на шагах 2–3 (фаза `needs-answer`): `grep`/`read` в
   `repositories/`, `run_shell_command` по коду, deep audit Java/proto. Варианты
   — из контекста и аналитики; код — только на шаге 4 apply, если Decision
   явно требует якоря.
4. Каждый label = **что зафиксируем в spec** + **какие § затронуты** (все GAP
   кластера).
5. Вариант «**Отложить**» — если gap не blocker или нет данных.
6. Не предлагать правки `repositories/`.

Порядок кластеров в батче: контракт / use case / BR → scope и поведение →
интеграция → NFR и prod-defaults → цель и метрики.

---

## Шаг 3. DECISIONS, не ask_user_question

Субагент **не** вызывает `ask_user_question` (в Qwen инструмент недоступен).
Протокол файла — правило `artifact-paths` § DECISIONS.

1. Прочитай `DECISIONS` (создай таблицу, если файла нет).
2. Есть `pending-apply` по открытым GAP/`Q-XX` → сразу Шаг 4.
3. По **кластеру** без строки Relates: не дублируй уже
   `applied`/`deferred`/`pending-apply`. Нет решения — **одна** строка
   `needs-answer` на кластер; в **Relates** перечисли **все** `GAP-*` кластера
   и `Q-XX`. Options = 2–4 варианта из шага 2.
4. Записал `needs-answer` для текущего батча → **`ASK_PARENT` и стоп**. Не
   продолжай apply, не исследуй код, не правь `SPEC`.
5. Все открытые кластеры уже в `needs-answer` без Decision → **стоп**, не
   плоди строки.

Оркестратор после опроса ставит `pending-apply` и запускает этот скилл снова.

## Шаг 4. Применить ответы

### 4.1 Принцип «чистая spec»

- ❌ Не добавлять журнал закрытия gaps и аналоги в `SPEC`.
- ❌ Не оставлять строки `Закрыт` в таблицах гэпов.
- ❌ Не оставлять inline `[GAP-...]` там, где решение зафиксировано.
- ✅ Переписать затронутые § под выбранный вариант — как если бы gap не было.
- ✅ Подтверждённое **Допущение** → обычный текст в §2 или релевантном §.

### 4.2 Правки `SPEC`

Для каждого gap с выбором **не «отложить»**:

1. Обновить все §, на которые влияет решение (согласованно).
2. **Удалить** строку gap из таблицы гэпов.
3. **Удалить** inline `[GAP-XXX]`; вместо placeholder — конкретное значение.
4. Не осталось строк в блоке → **удалить** подзаголовок и пустую таблицу.
5. Legacy `## Журнал закрытия gaps` → удалить, данные перенести в `GAPS_MAP`.

Отложенные gaps — **не трогать** в `SPEC`; перечислить в карте как «отложено».
Новые BR без решения пользователя **не выдумывать**.
В `DECISIONS` у применённых строк Status → `applied`; у «отложить» → `deferred`.

### 4.3 Карта закрытых gaps

Запиши `GAPS_MAP` (не в `SPEC`). Шаблон — [reference.md](reference.md)
§ «Выходной файл». Повторный прогон — **append** секции `## Сессия N`.

### 4.4 Обратная запись в `CONTEXT_DOC`

Для каждого закрытого gap со связанным `Q-XX` — допиши в `CONTEXT_DOC` секцию
`## Закрытые вопросы` (создай, если нет), **не удаляя** строку из «Открытые вопросы»:

```markdown
## Закрытые вопросы

| ID | Дата | Решение | Где в spec | Источник |
|----|------|---------|------------|----------|
| Q-04 | 2026-08-28 | Доходность в `HistoryOperationLead.yield` (PriceData) | §4.1.1, §4.2.3 | /resolve-gaps (GAP-INT-05) |
```

Так `CONTEXT_DOC` не отстаёт от `SPEC`, а `/feature-status` корректно считает
открытые `Q-XX`. Остальные § контекст-документа **не менять**.

---

## Шаг 5. Ответ и перепроверка

После записи `GAPS_MAP` обнови якоря контекста (не переписывай current-state):

```bash
python3 scripts/refresh_context.py <slug>
```

Кратко на русском: опрошено / закрыто / отложено; пути `SPEC`, `GAPS_MAP`;
список закрытых id.

**Next step** — по матрице:

| Что изменилось | Рекомендация |
|----------------|--------------|
| Правки затронули BR/CN, use case, контракты | `/check-feature <slug>` — согласованность |
| Правки затронули только формулировки | `/check-feature-code` если `CHALLENGES` уже есть; иначе `/challenge-feature` |
| `ALIGNMENT` уже существовал | он **устарел** → повторный `/check-feature-code <slug>` |
| Сомнение, что дальше | `/feature-status <slug>` |
