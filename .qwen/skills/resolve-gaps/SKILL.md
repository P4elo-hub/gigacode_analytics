# resolve-gaps

Интерактивное **закрытие** открытых gaps: реестр `[GAP-...]` → кластеры по
`Q-XX` → варианты в `DECISIONS` → оркестратор спрашивает → переписать § `SPEC`
и **удалить** маркеры. Карта — в `GAPS_MAP`, не в теле спецификации.

Каждый открытый `[GAP-...]` этот шаг закрывает. Факт в `CONTEXT_DOC` /
`analytics/` / sibling-контексте → вычеркнуть без опроса. Нет факта →
`needs-answer` → вопрос пользователю → apply → маркер снят. **Запрещено**
Status `deferred`, вариант «Отложить», оставлять гэп «на потом».

Отличие от `/resolve-code-alignment`: источник — **сама спецификация** и
контекст-док, а не отчёт `ALIGNMENT`.

Пути и токены: правило `artifact-paths`.

## Pipeline

```
/write-feature → /check-feature → /resolve-gaps → /challenge-feature → …
```

| | Путь |
|---|------|
| **Вход** | `SPEC` = `Feature-writing/<slug>/<slug>.md` |
| **Контекст** | `CONTEXT_DOC` = `Feature-context/<slug>.md` (если есть) |
| **Ответы** | `DECISIONS` = `Feature-writing/<slug>/<slug>-decisions.md` |
| **Правим** | `SPEC` (содержательные §) + `CONTEXT_DOC` (§ закрытых Q) |
| **Выход (карта)** | `GAPS_MAP` = `Feature-writing/<slug>/<slug>-gaps-resolved.md` |
| **Не трогаем** | `repositories/`, `ALIGNMENT`, `CHALLENGES` |

Детали извлечения gaps и шаблоны вариантов: [reference.md](reference.md).

---

## Шаг 0. Разрешить slug

1. Аргумент: `<slug>` **или** путь к `SPEC`.
2. Нет `SPEC` → стоп: сначала `/write-feature`.
3. Опциональный **фокус** — список `GAP-...` / `Q-XX` (только их опросить).

---

## Шаг 1. Собрать реестр открытых gaps

Не читать `SPEC` cover-to-cover. Реестр — `grep`, формулировки `Q-XX` — `CONTEXT_DOC`.

1. `grep` `GAP-[A-Z0-9-]+` по `SPEC` (content) — полный список id и строк.
2. Прочитай `CONTEXT_DOC` целиком (бриф, «Открытые вопросы», что уже подтверждено).
3. На каждый уникальный GAP — только строку таблицы `**Gaps и допущения:**` или
   ~30–40 строк вокруг маркера (заголовок § + формулировка). Не читай главы
   NFR/OBS/алгоритм целиком, пока GAP оттуда не попал в батч 1.
4. После сжатия контекста **не** начинай `SPEC` с строки 1: повтори `grep`,
   не полный read. Реестр id уже есть — не пересобирай его чтением файла.

| Источник | Как искать |
|----------|------------|
| Таблицы `**Gaps и допущения:**` | Строки с `Тип` = `Gap` / `Допущение`; строки `Закрыт` (legacy) — мигрировать в карту и удалить из `SPEC` |
| Inline-маркеры | `[GAP-...]` — через `grep`, не линейным чтением файла |
| Связанные `Q-XX` | Q из `CONTEXT_DOC`, на которые ссылается gap |

Открытый гэп — любой `[GAP-…]` / строка таблицы без «закрыт»/`closed`. Слова
«отложено» / `deferred` в строке **не** делают гэп закрытым: его всё ещё
надо спросить и снять.

### Дедупликация и исключения

- Один `GAP-*` id — **один** след в spec, даже если встречается в нескольких §.
- **Единица опроса — кластер**, не отдельный GAP: несколько GAP на один `Q-XX` →
  **одна** строка `DECISIONS`, все id в колонке Relates.
- GAP без явного Q в строке — привяжи по смыслу к `Q-XX` из `CONTEXT_DOC` §
  «Открытые вопросы» или sibling GAP с тем же текстом (см. [reference.md](reference.md)
  § «Кластеризация»).
- Исключать: GAP как TO BE implementation, дубликаты без нового смысла.

Если **открытых gaps = 0** → сообщи и **стоп** (файлы не править).

### 1.1 Кластеризация (обязательно, до вариантов)

1. Собери уникальные `GAP-*` из `SPEC`.
2. Для каждого GAP найди связанный `Q-XX` (inline, таблица, context-doc).
3. Сгруппируй: `Q-01 → [GAP-GOAL-04, GAP-INT-01, …]`.
4. Выведи таблицу кластеров в ответ оркестратору (Q / GAP count / ids).
5. **Не** обрабатывай GAP по одному — только кластеры.

| Открытых GAP | Батч needs-answer |
|--------------|-------------------|
| ≤ 15 | все кластеры одним проходом |
| > 15 | **батч 1:** blockers (контракт, UC, BR); **батч 2+:** после apply батча 1 — тоже опрос, не отклад |

---

## Шаг 2. Подготовить варианты решения

Для **каждого кластера батча** (Q-XX или группа orphan GAP с одной темой)
сформируй 2–4 **конкретных** варианта до опроса. Не делай второй проход `SPEC`.

1. Источники по приоритету: `CONTEXT_DOC` → один `grep` по теме фичи в
   `analytics/` (пропусти, если контекст уже фиксирует «совпадений нет») →
   sibling **CONTEXT_DOC** или якорь § (`yield` / тип поля / уровень), **не**
   sibling-спеку целиком.
2. На кластер батча 1 — один короткий read § вокруг GAP (строка таблицы или
   ~30–40 строк). Префикс `GAP-NFR-*` сам по себе не отправляет id в батч 2:
   смотри формулировку строки.
3. ❌ На шагах 2–3: `grep`/`read` в `repositories/`, `run_shell_command` по коду,
   deep audit Java/proto. Код — только на шаге 4 apply, если Decision требует якоря.
4. Каждый label = **что зафиксируем в spec** + **какие § затронуты** (все GAP
   кластера). Все варианты — закрытие: значение, принятое допущение, или
   «вне scope» как CN/ограничение. После любого выбора маркер снимается.
5. Нет данных в источниках — **не** повод молчать. Это повод `needs-answer`.
   Вариант «Отложить» **запрещён**. Status `deferred` **запрещён**.
6. Как только есть кластеры батча и 2–4 варианта — сразу Шаг 3. Запрещён
   повторный полный проход `SPEC` «для уверенности». Нет write к этому моменту
   → всё равно пиши собранное и стоп.

Порядок кластеров в батче: контракт / use case / BR → scope и поведение →
интеграция → NFR и prod-defaults → цель и метрики.

---

## Шаг 3. DECISIONS, не ask_user_question

Субагент **не** вызывает `ask_user_question` (в Qwen инструмент недоступен).
Протокол файла — правило `artifact-paths` § DECISIONS.

1. Прочитай `DECISIONS` (создай таблицу, если файла нет).
2. Есть `pending-apply` по открытым GAP/`Q-XX` → сразу Шаг 4.
3. По **кластеру** без строки Relates: не дублируй уже `applied` /
   `pending-apply`. `deferred` / Decision «Отложить» при живом маркере в
   SPEC — **не** закрыто: перепиши строку в `needs-answer` и спроси заново.
   Нет решения — **одна** строка `needs-answer` на кластер; в **Relates**
   перечисли **все** `GAP-*` кластера и `Q-XX`. Options = 2–4 варианта из шага 2.
4. Записал `needs-answer` для текущего батча → **`ASK_PARENT` и стоп**. Не
   продолжай apply, не исследуй код, не правь `SPEC`.
5. Все открытые кластеры уже в `needs-answer` без Decision → **стоп**, не
   плоди строки.

Оркестратор после опроса ставит **только** `pending-apply` (для GAP никогда
`deferred`) и запускает этот скилл снова.

## Шаг 4. Применить ответы

Единица правки = **Decision + его §**, не файл целиком и не одна ячейка.

### 4.1 Карта, не cover-to-cover

1. Все строки `pending-apply` в `DECISIONS` (этот батч).
2. `grep` по Relates (`GAP-*`, `Q-XX`) → список затронутых **§**.
3. **Не** читай `SPEC` с строки 1. Главы вне Relates этого батча не открывай.
4. После сжатия контекста: `grep` оставшихся `pending-apply` → следующий §;
   **запрещено** «прочитать SPEC целиком чанками».

### 4.2 Принцип «чистая spec»

- ❌ Не добавлять журнал закрытия gaps и аналоги в `SPEC`.
- ❌ Не оставлять строки `Закрыт` в таблицах гэпов.
- ❌ Не оставлять inline `[GAP-...]` там, где решение зафиксировано.
- ✅ Переписать затронутый § под выбранный вариант — как если бы gap не было.
- ✅ Подтверждённое **Допущение** → обычный текст в §2 или релевантном §.

### 4.3 Правка по кластеру §

Один `D-*` за раз, его § по очереди. Закончил § — выкинь его из контекста.

| Тип § | Как править |
|-------|-------------|
| Use case / алгоритм / контракт, смысл меняется | Прочитай **весь этот §** и перепиши **целиком** |
| Таблица гэпов в том же § | В том же rewrite: удалить строки Relates, пустой блок — снести |
| Inline `[GAP-…]` в том же § | В том же rewrite: конкретное значение, маркер убрать |
| Два несмежных § у одного Decision | Два вызова (по §), не сорок точечных замен |

Один `edit`/`write` на непрерывный кусок §, не 8 замен по маркерам.
`repositories/` на apply — только если Decision требует code anchor.
Sibling-спеку целиком не грузи.

Новые BR без решения пользователя **не выдумывать**. После apply в SPEC
не должно остаться `[GAP-…]` этого батча.

### 4.4 Статусы и housekeeping — **один раз в конце**

Когда все § батча переписаны:

1. В `DECISIONS`: применённые → `applied`. Для GAP не писать `deferred`.
2. `GAPS_MAP` (шаг 4.5).
3. `CONTEXT_DOC` § «Закрытые вопросы» (шаг 4.6).

Не мешай housekeeping с правкой середины файла.

### 4.5 Карта закрытых gaps

Запиши `GAPS_MAP` (не в `SPEC`). Шаблон — [reference.md](reference.md)
§ «Выходной файл». Повторный прогон — **append** секции `## Сессия N`.

### 4.6 Обратная запись в `CONTEXT_DOC`

Для каждого закрытого gap со связанным `Q-XX` — допиши в `CONTEXT_DOC` секцию
`## Закрытые вопросы` (создай, если нет), **не удаляя** строку из «Открытые вопросы»:

```markdown
## Закрытые вопросы

| ID | Дата | Решение | Где в spec | Источник |
|----|------|---------|------------|----------|
| Q-04 | 2026-08-28 | Доходность в `HistoryOperationLead.yield` (PriceData) | §4.1.1, §4.2.3 | /resolve-gaps (GAP-INT-05) |
```

Так `CONTEXT_DOC` не отстаёт от `SPEC`, а `/feature-status` корректно считает
открытые `Q-XX`. Остальные § контекст-документа **не менять**.

---

## Шаг 5. Ответ и перепроверка

После записи `GAPS_MAP` обнови якоря контекста (не переписывай current-state):

```bash
python3 scripts/refresh_context.py <slug>
```

Кратко на русском: опрошено / закрыто; пути `SPEC`, `GAPS_MAP`; список закрытых id.
Если в SPEC ещё есть `[GAP-…]` — это не «готово»: следующий батч `needs-answer`.

**Next step** — по матрице:

| Что изменилось | Рекомендация |
|----------------|--------------|
| Правки затронули BR/CN, use case, контракты | `/check-feature <slug>` — согласованность |
| Правки затронули только формулировки | `/check-feature-code` если `CHALLENGES` уже есть; иначе `/challenge-feature` |
| `ALIGNMENT` уже существовал | он **устарел** → повторный `/check-feature-code <slug>` |
| Сомнение, что дальше | `/feature-status <slug>` |

## Антипаттерны

- ❌ Читать `SPEC` cover-to-cover на фазе `needs-answer`
- ❌ После сжатия контекста заново читать `SPEC` с строки 1
- ❌ Читать sibling-спеку целиком вместо sibling `CONTEXT_DOC` / якоря §
- ❌ Обрабатывать **каждый GAP отдельно** вместо кластера по `Q-XX`
- ❌ `grep`/`read` в `repositories/` до записи `needs-answer` в `DECISIONS`
- ❌ Продолжать работу после `needs-answer` без `ASK_PARENT` и стоп
- ❌ >15 GAP и пытаться опросить всё за один проход (нарушение батча)
- ❌ Править `SPEC` до `pending-apply` / `applied` в `DECISIONS`
- ❌ На apply править по одному `[GAP-…]` вместо целого § кластера
- ❌ После сжатия на apply читать `SPEC` с строки 1 / «чанками целиком»
- ❌ Грузить sibling-спеку или `repositories/` на apply без нужды Decision
- ❌ Звать `ask_user_question` из субагента
- ❌ Переспрашивать GAP/`Q-XX`, уже `applied` или `pending-apply` в Relates
- ❌ Писать карту закрытых gaps **внутри** `SPEC`
- ❌ Оставлять строки `Закрыт` вместо удаления
- ❌ Закрывать GAP без явного выбора пользователя (кроме факта из источника)
- ❌ Status `deferred` / вариант «Отложить» / оставлять `[GAP-…]` после apply
- ❌ Править § `CONTEXT_DOC` кроме «Закрытые вопросы» и блока,
  который пишет `scripts/refresh_context.py`
- ❌ Менять код в `repositories/`
