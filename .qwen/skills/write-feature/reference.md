# write-feature — reference

## Блоки документа

Полный перечень блоков, профилей и kit — `kb-writing-kits/spec-catalog.yaml`.
Профиль по умолчанию — `sihist`. Keyword **только добавляет** редкие блоки
(async, threat, acceptance, migration, C4). Оркестратор уточняет исключения
через `ask_user_question`.

Колонка **Скиллы** плана — единственный список, который грузит writer.
Базовые скиллы блока + `section_skills` только для активных разделов
(поле `skills` / `section_skills` в каталоге).

План печатает раздел **Задания spec-writer**: оркестратор копирует блок
`### \`<id>\`` в task целиком (строка `skills:` — все скиллы).

После записи фрагмента оркестратор гоняет `check-part` **один** раз
(всегда `--block-id` и `--sections` утверждённого плана):

```bash
python3 scripts/write_feature.py "<бриф>" --mode check-part --name <slug> \
  --block-id <id> --part-dir Feature-writing/<slug> --sections "<план>"
```

Отказ `check-part` — фрагмент пустой или нет PlantUML при `uml-diagram-analysis`.
Форма раздела — template/gate kit. План — оркестратор.

## Правила черновика (Проход 1)

### Формат фрагмента

- только Markdown **этого** блока;
- без `# заголовка документа` и без родительских `## 1.` / `## 3.` / `## 4.` / `## 5.`
  (раздел `## 2.` оставляй);
- без обёртки ```markdown;
- без служебных строк: `INTERNAL`, `> **Kit`, `> **Skill`, `Раздел X | kit`.

### Use Case: уровень сценария

**Нельзя** в AS IS / TO BE: внутренние классы, обёртки, конвертеры, мапперы,
фабрики, DTO-генераторы (`BphRawLinkedEventsWrapper`, leaf-конвертеры).

**Можно**: участвующий сервис, контракт, endpoint, имена полей и параметров.

Технические имена классов — только в §3 (архитектура), §4.1.x (интеграции),
§4.2.3 (модель данных).

Состав таблиц UC и контракта — template/gate kit этого блока. Не дублируй
форму здесь и не сжимай относительно kit.

### Гэпы

Чего нет в брифе / `CONTEXT_DOC` / kit → строка в таблице «Gaps и допущения»
по quality gate блока:

```markdown
**Gaps и допущения:**

| ID | Тип | Где обнаружено | Что не хватает / что предполагается | Как закрыть |
|----|-----|----------------|-------------------------------------|-------------|
| GAP-INT-03 | Gap | Параметр запроса (Q-03) | Не определено, нужен ли параметр для возврата поля | Команда ОГ |
```

Схема id: `GAP-<БЛОК>-NN`, где блок — короткий код (`GOAL`, `UCAS`, `UCTB`,
`CONS`, `INT`, `DM`, `MAP`, `NFR`).

Связывай гэп с `Q-XX` из `CONTEXT_DOC` в колонке «Где обнаружено» — это нужно
для обратной записи в context-doc при `/resolve-gaps`.

## Правила закрытия гэпов (Проход 2)

| Тип факта | Где искать | Приоритет |
|-----------|------------|-----------|
| Бизнес-требование, AS IS | `analytics/` | 1 |
| Контракт, поле, класс, миграция | `repositories/` | 1 |
| Схема БД | `db-export/` | 2 (код важнее) |
| Согласование с соседней фичей | `Feature-writing/*/` | 2 |

Правило: подтверждено цитатой с путём → факт; иначе гэп остаётся.

## Traceability

| ID | Где | Правило |
|----|-----|---------|
| `BR-01…` | §1.1 таблица бизнес-правил | Источник / обоснование обязателен |
| `CN-01…` | §1.1 / §2 | Ограничения и допущения |
| `[GAP-...]` | таблицы гэпов + inline | Не удалять без источника |
| `Q-XX` | ссылка на `CONTEXT_DOC` | В колонке «Где обнаружено» |

Шаги use case ссылаются на `[BR-XX]`, когда правило применяется.

## Сборка и проверка

```bash
python3 scripts/write_feature.py "<бриф>" --mode assemble --name <slug> \
  --part-dir Feature-writing/<slug> \
  --out Feature-writing/<slug>/<slug>.md
```

Успешный `--out` удаляет `*.part-*.md` и `*.context.md`.
Неполный assemble (нет фрагмента) рабочие файлы не трогает.

Self-check перед финалом:

- [ ] Порядок глав как в плане / `kb-writing-kits/spec-catalog.yaml`
- [ ] Нет служебных строк и обёрток
- [ ] Контракты полные, новые поля помечены
- [ ] Use Case без кодовой детализации
- [ ] Каждый блок имеет таблицу гэпов (если гэпы есть)
- [ ] Незакрытые `[GAP-...]` сохранены
- [ ] Язык русский; имена полей/API — как в исходниках
- [ ] Файл лежит в `FEATURE_DIR`
