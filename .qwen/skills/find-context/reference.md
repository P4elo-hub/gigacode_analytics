# find-context — reference

## Области поиска и приоритеты

| Область | Путь | Что даёт | Приоритет |
|---------|------|----------|-----------|
| Аналитика | `analytics/` | Confluence-экспорт, требования, AS IS / TO BE | Бизнес-факты — **первый** |
| Спецификации фич | `Feature-writing/*/` | Соседние и прошлые фичи, согласование контрактов | Reference |
| Код и контракты | `repositories/` | proto, OpenAPI, entity, миграции, конфиги | Технические факты — **первый** |
| Данные | `db-export/` | DDL, справочники, текущая схема | Справочник (код важнее) |
| Доп. материалы | `auxiliary/` | Прочее, если есть | Последний |

## Скрипт: типичные вызовы

```bash
# базовый
python3 scripts/find_context.py "<бриф>" --name <slug> --out Feature-context/<slug>-discovery.md

# усилить термины (доменные имена, сервисы, поля)
python3 scripts/find_context.py "<бриф>" --name <slug> --terms "GetTradeOrders order-gateway yield" \
  --out Feature-context/<slug>-discovery.md

# расширить выдачу
python3 scripts/find_context.py "<бриф>" --name <slug> --doc-limit 40 --code-limit 60 \
  --out Feature-context/<slug>-discovery.md
```

Скрипт ищет рекурсивно, поэтому папки фич `Feature-writing/<slug>/` попадают в выдачу.

По брифу определяется **фокус** (`scripts/discovery_focus.py`):

| Фокус | Когда | Сначала открыть | Якоря в CONTEXT_DOC |
|-------|-------|-----------------|---------------------|
| `integration` | grpc / proto / rest / контракт | `*.proto`, RPC | service, rpc, message, поля |
| `data` | миграция / таблица / liquibase | changelog, `db-export/` | таблица, колонка, changeset |
| `mixed` | оба признака | оба списка | оба набора якорей |
| `general` | нет явных признаков | proto и DDL, если есть в выдаче | контракт + данные, если затронуты |

`*.proto` и liquibase получают бонус к score **только если** уже совпали
термины брифа — скрипт не подмешивает слово `proto` во все файлы.

## Что считается подтверждённым фактом

| Утверждение | Чем подтверждается |
|-------------|--------------------|
| «Метод X существует» | путь к файлу + строки + сигнатура |
| «Поле Y типа Z» | proto / OpenAPI / `@Column` с цитатой |
| «Таблица T содержит колонку C» | миграция или `db-export/` + entity |
| «Конфиг K имеет default D» | `application*.yml` / `@DefaultValue` |
| «Флаг F управляет поведением B» | константа + `if` / strategy в коде |

Нет цитаты с путём → это **не факт**, а `Q-XX`.

## Формулировка Q-XX

Плохо:

```markdown
| Q-01 | Уточнить поле | — |
```

Хорошо:

```markdown
| Q-01 | Финальное имя поля «доходность» в proto ОГ, `history.yml` и BDUI — `yield`, `profitability` или иное? | Владельцы контрактов ОГ и screen-api; см. Q-01 в `bph-linked-events-yield` |
```

Требования к `Q-XX`:

- один вопрос = одно решение;
- сформулирован так, что на него можно ответить выбором из вариантов;
- указан адресат или файл, где искать ответ;
- нумерация сквозная в рамках `<slug>`.

## Связь Q-XX → дальше по pipeline

| Куда попадает | Как |
|---------------|-----|
| `SPEC` | `/write-feature` превращает непокрытые Q в `[GAP-...]` соответствующего блока |
| `GAPS_MAP` | `/resolve-gaps` фиксирует решение и связанный `Q-XX` |
| `CONTEXT_DOC` § «Закрытые вопросы» | resolve-скиллы дописывают закрытые Q (обратная связь) |

Поэтому качество `Q-XX` напрямую определяет качество опроса в `/resolve-gaps`.

- [ ] Каждый факт имеет путь + якорь
- [ ] Нет `INTERNAL`, score-таблиц, служебных строк
- [ ] Нет проектирования TO BE
- [ ] Все непроверенные утверждения → `Q-XX`
